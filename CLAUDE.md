# Galla Mandi — server

This repo is the **API** (NestJS). It is the only place that reads or writes the database.

Galla Mandi is a **multi-tenant SaaS** for grain-market (galla mandi) commission shops in Pakistan.
Every shop is one **tenant** with one `tenant_id`; the shop owner gets one account and adds staff.

| Repo | What it is |
|---|---|
| `server` | NestJS + PostgreSQL + Drizzle REST API (the only thing that talks to the database) |
| `web` | Next.js shop panel for owners and staff |
| `admin` | Next.js super-admin panel for the platform team |
| `app` | React Native + Expo mobile app for owners and staff |

Roles: `super_admin` (platform, no tenant), `owner`, `manager`, `operator` (per shop).

## How to work on a ticket

Every issue is one ticket from the org board **Gala Mandi**. Each ticket has: Design & references,
Summary, What we'll use and why, Tasks, Scenarios, Testing, Done when.

1. Read the whole issue first. Only do the part that belongs to **this repo**: tasks are often
   prefixed `**server:**`, `**web:**`, `**admin:**`, `**web + admin:**`, `**all repos:**`.
2. Use the references in the ticket:
   - **Tables:** `docs/database/schema.dbml` (the ER diagram link in the ticket shows the same design).
   - Screens are in the `web`, `admin` and `app` repos; you only need their texts (error messages).
3. Do every task for this repo. Cover the **Scenarios** in code and write the tests from **Testing**
   that apply to this repo.
4. Stay inside the ticket. Don't add libraries, tables, endpoints or pages the ticket doesn't ask for.
   Use the tools listed in "What we'll use, and why"; if you must use something else, say why in the PR.
5. If something is unclear, missing or contradicts another file, ask in a comment on the issue
   instead of guessing. Don't stop half-way silently.
6. Before you finish: lint, type-check and all tests must pass.
7. Commits use Conventional Commits (`feat(auth): add refresh rotation`). The pull request
   description must contain `Closes #<issue number>`, the ticket's tasks as a checklist (ticked
   for what's done), how to run/test it, and anything left for a follow-up ticket.

## Domain rules (all repos)

- **Words used in the business:** kissan = farmer (seller), beopari = buyer, arhti = commission agent
  (the shop), parchi = bill/receipt, khata = ledger, kanta = weighing scale, peshgi = advance,
  mann/maund = 40 kg, bori = bag.
- **Money:** `numeric(14,2)` in the DB. Never use JS `number`/float maths for money: send money as
  strings in the API and use `decimal.js` for calculations. Rupees, 2 decimals.
- **Weight:** stored in kg as `numeric(12,3)`. 1 maund = 40 kg. Show maund + kg in the UI
  (e.g. `12 mn 15 kg`).
- **Ledger (khata) is append-only.** Never update or delete a ledger entry; correct it with a
  reversing entry.
- **Bill (parchi) numbers** are per shop and come from `number_sequences`; no gaps from failed saves.
- **Time:** store `timestamptz` (UTC); show Asia/Karachi time.
- **Language:** English now, Urdu (RTL) later. Keep user-facing text out of logic so it can be
  translated; use logical CSS (`ms-`, `me-`, `start`, `end`) instead of left/right.
- **Never trust the client** with `tenant_id`, role, prices or totals: the server decides.

## Stack

| Area | Tool |
|---|---|
| Framework | NestJS + TypeScript (strict) |
| Database | PostgreSQL + Drizzle ORM + drizzle-kit migrations |
| Validation | Zod (`nestjs-zod`); config validated with Zod via `@nestjs/config` |
| Auth | `@nestjs/jwt` + passport-jwt, argon2, refresh-token rotation |
| Request context | `nestjs-cls` (holds `tenantId`, `userId`, `role`) |
| Docs | `@nestjs/swagger` at `/docs` |
| Security | helmet, CORS allow-list, `@nestjs/throttler` |
| Logs | `nestjs-pino` |
| Tests | Jest (unit), Jest + supertest (e2e) against a real Postgres from Docker Compose |
| Package manager | npm |

## Folder layout

```
src/
  modules/<feature>/      controller, service, dto (Zod schemas), <feature>.spec.ts
  common/                 guards, decorators (@CurrentUser, @CurrentTenant, @Roles), filters, interceptors
  database/schema/        one Drizzle file per table (names match docs/database/schema.dbml)
  database/migrations/    generated by drizzle-kit, never edited after they are merged
  config/                 Zod env schema
test/                     e2e tests (supertest)
docs/database/schema.dbml the database design (same as the ER diagram)
```

## Database

- `docs/database/schema.dbml` is the database design. Table names, column names, types and
  relations in Drizzle **must match it**. If a ticket needs a change to it, change the Drizzle
  schema, generate a migration, and say in the PR that `schema.dbml` (master copy in
  `gala-mandi/.github`) needs the same update. Don't edit `docs/database/schema.dbml` here; it is
  overwritten by the sync from `gala-mandi/.github`.
- One migration per change (`drizzle-kit generate`). Never edit a migration that is already merged.
- Primary keys are `uuid`. Soft delete with `deleted_at`.

## Multi-tenant rules (must follow on every change)

- Every business table has `id`, `tenant_id` (NOT NULL, FK to `tenants`), `created_at`,
  `updated_at`, `created_by`, `deleted_at`, and indexes that start with `tenant_id`.
- `tenantId` comes **only from the JWT** (via CLS), never from the body, params or query. A
  `tenant_id` sent by the client is ignored.
- All queries on business tables go through the tenant-scoped helper; Row-Level Security is the
  second layer. Another shop's record by ID returns `404`, never `403`, so IDs can't be probed.
- Every new endpoint gets an e2e isolation test with two seeded tenants (read, update, delete
  across tenants must fail).
- Only `super_admin` can cross tenants, through `withTenant()`, and every such action is written
  to `audit_logs`.
- Roles are checked with `@Roles()` + `RolesGuard`; suspended tenants and inactive users get `403`.

## API conventions

- REST, plural nouns: `GET /traders`, `POST /traders`, `PATCH /traders/:id`, `DELETE /traders/:id`.
- Lists accept `?page=&limit=&search=&sort=` and return `{ data, meta: { page, limit, total } }`.
- Errors are JSON: `{ statusCode, message, errors? }`; no stack traces outside development.
- Every endpoint has Swagger decorators and a Zod DTO.
- Writes that move money or stock run in one DB transaction.
- Secrets only in env; keep `.env.example` up to date.
