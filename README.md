# Galla Mandi — server

REST API for Galla Mandi, built with NestJS, PostgreSQL and Drizzle ORM. It is the only part of the system that talks to the database.

## Requirements

- Node.js 24 (see `.nvmrc`; 22.12+ also works)
- npm
- Docker with Docker Compose

## Setup

```bash
git clone git@github.com:gala-mandi/server.git
cd server
cp .env.example .env          # then change POSTGRES_PASSWORD and DATABASE_URL
npm install
docker compose up -d          # starts Postgres
npm run db:migrate            # creates the tables
npm run db:seed               # super-admin + demo shop owner (passwords from .env)
npm run dev                   # API on http://localhost:4000
```

- Health check: <http://localhost:4000/health>
- API docs (Swagger): <http://localhost:4000/docs>

If port 5432 is already used on your machine, set `POSTGRES_PORT` in `.env` (for example `55432`) and use the same port in `DATABASE_URL`.

## Environment variables

Every variable is listed in `.env.example`. They are checked with Zod when the app starts. A missing or wrong value stops the app with a message that names each bad variable, for example:

```
Error: Invalid environment variables:
  - DATABASE_URL: Invalid input: expected string, received undefined
```

Never commit `.env`.

## What is set up

- **Config:** `@nestjs/config` + Zod (`src/config/env.schema.ts`)
- **Database:** global `DatabaseModule` gives `TenantDatabase` for shop data (see [Multi-tenant data](#multi-tenant-data-how-to-add-a-business-table)) and the raw Drizzle instance (`@Inject(DRIZZLE)`) for `auth` and `health` only. First migration creates `tenants` and `users`.
- **Validation:** global `ZodValidationPipe` (nestjs-zod). DTOs are Zod schemas.
- **Errors:** every error is JSON `{ statusCode, message, errors? }`. Validation errors list `errors: [{ field, message }]`. Stack traces are logged, never returned.
- **Security:** helmet, CORS allow-list (`CORS_ORIGINS`), rate limit with `@nestjs/throttler` (`THROTTLE_LIMIT` per `THROTTLE_TTL_MS`, `429` when over).
- **Logs:** nestjs-pino (JSON). `Authorization` and `Cookie` headers are redacted.
- **Docs:** Swagger UI at `/docs`, OpenAPI JSON at `/docs-json`.

## Authentication

| Endpoint                                                  | Auth   | What it does                                                                            |
| --------------------------------------------------------- | ------ | --------------------------------------------------------------------------------------- |
| `POST /auth/login`                                        | —      | Phone or email + password. Returns an access token and sets the `refresh_token` cookie. |
| `POST /auth/refresh`                                      | cookie | Rotates the refresh token and returns a new access token.                               |
| `POST /auth/logout`                                       | cookie | Ends this session and clears the cookie.                                                |
| `POST /auth/logout-all`                                   | Bearer | Ends every session of the user.                                                         |
| `GET /auth/me`                                            | Bearer | The current user and shop.                                                              |
| `POST /auth/change-password`                              | Bearer | Ends the user's other sessions.                                                         |
| `POST /auth/forgot-password`, `POST /auth/reset-password` | —      | 6-digit code, then a new password. Ends every session.                                  |

- **Access token:** JWT (HS256), 15 minutes, payload `{ sub, tenantId, role, sid }`. Clients keep it in memory.
- **Refresh token:** random, stored as a SHA-256 hash in `refresh_tokens`, sent as an `httpOnly`, `SameSite=Lax` cookie (`Secure` outside development). 7 days with "keep me signed in", otherwise a browser-session cookie. Each refresh revokes the old token; using a rotated token again ends every session of that user.
- **Errors:** `401 Invalid credentials` (same for unknown users), `403` with `code: ACCOUNT_DISABLED` or `TENANT_SUSPENDED`, `401` with `code: SESSION_EXPIRED`, `400` with `code: INVALID_OTP`.
- **Brute force:** `LOGIN_THROTTLE_LIMIT` (5) tries per minute for each IP + phone/email on login and forgot-password, then `429` with `Retry-After`.
- **Logs:** every login, logout, failed try, refresh, lock-out and reset goes to `auth_logs`. Passwords, tokens and codes are never logged.
- **OTP:** sent through the `OtpSender` interface (`src/modules/auth/otp/otp-sender.ts`). There is no WhatsApp/SMS provider yet: in development the code is written to the server log, elsewhere nothing is sent. Add a provider by binding another `OtpSender` to `OTP_SENDER`.
- **In code:** protect a route with `@UseGuards(JwtAuthGuard, TenantGuard, RolesGuard)`, read the user with `@CurrentUser()`, the shop with `@CurrentTenant()` (always from the token), and limit roles with `@Roles('owner')`.
- **Behind a proxy:** set Express `trust proxy` so `req.ip` (used for rate limits and logs) is the client's address.

## Database changes

1. Edit or add a file in `src/database/schema/`. Table and column names must match `docs/database/schema.dbml`.
2. Run `npm run db:generate` and commit the new migration.
3. Run `npm run db:migrate`.

Never edit a migration that is already merged.

## Multi-tenant data (how to add a business table)

Every shop is a tenant. A shop must never see another shop's rows. Two layers make sure of that:

1. **The query helper** adds `WHERE tenant_id = <shop>` to every query and sets `tenant_id` on every insert.
2. **Row-Level Security (RLS)** in Postgres blocks other shops' rows, even if a query forgets the helper.

### 1. The table

- Start with `tenantColumns()` (`src/database/tenant-table.ts`). It adds `id`, `tenant_id` (NOT NULL, FK to `tenants`), `created_by`, `created_at`, `updated_at` and `deleted_at`.
- Every index starts with `tenant_id`, for example `(tenant_id, created_at)`. List queries then use the index.
- Unique constraints are per shop: `UNIQUE (tenant_id, phone)`, never `UNIQUE (phone)`. Two shops may have the same trader phone.
- Add `tenantIsolation()` to the table extras. `npm run db:generate` then writes `ENABLE ROW LEVEL SECURITY` and the `tenant_isolation` policy into the migration.

```ts
// src/database/schema/traders.ts
export const traders = pgTable(
  'traders',
  {
    ...tenantColumns(),
    name: varchar('name', { length: 120 }).notNull(),
    phone: varchar('phone', { length: 20 }),
  },
  (t) => [
    index('traders_tenant_id_created_at_idx').on(t.tenantId, t.createdAt),
    uniqueIndex('traders_tenant_id_phone_key').on(t.tenantId, t.phone),
    tenantIsolation(),
  ],
);
```

### 2. The service

- Inject `TenantDatabase` (never `DRIZZLE`).
- Run each request's work in `transaction(({ scoped, tx }) => …)`. One call is one DB transaction.
- `scoped(table)` gives `findMany`, `findById`, `count`, `insert`, `update`, `softDelete` and `restore`. Reads always filter on the shop and skip soft-deleted rows; `whereWithDeleted()` includes them (for reports that must still show a deleted trader's name).
- Every write through `scoped()` also writes `audit_logs` in the same transaction (see "Audit log"). `update` returns the row or `null`, `softDelete` returns `true`/`false`.
- For paging, sorting or joins, write the query on `tx` and use `scoped(table).where(...)` or `.byId(id)` as the `WHERE`. They carry the tenant filter.
- Another shop's id is "not found": return `404`, never `403`, so ids can't be probed.

```ts
@Injectable()
export class TradersService {
  constructor(private readonly db: TenantDatabase) {}

  update(id: string, dto: UpdateTraderDto) {
    return this.db.transaction(async ({ scoped }) => {
      const row = await scoped(traders).update(id, dto);
      if (!row) throw new NotFoundException('Trader not found');
      return row;
    });
  }
}
```

### Where the shop comes from

- The shop id comes **only from the access token**. The JWT strategy puts `tenantId`, `userId` and `role` in the request context (nestjs-cls). `TenantDatabase` reads it from there.
- Never take `tenant_id` from the body, params or query. `StripTenantIdMiddleware` removes `tenant_id` and `tenantId` from every JSON body, also inside nested objects and arrays. `scoped().insert()` and `update()` drop them again and set the shop from the token.
- A token without a shop gets `403` on shop endpoints (`TenantGuard`).

### Super-admin access to a shop

- `super_admin` has no shop. It can open one only with `tenantDb.withTenant(tenantId, fn)`.
- Each call first writes a row to `audit_logs` with `action = 'access'`, then runs `fn` inside that shop. Any other role gets `403`.

### Why RLS works even when the API connects as a superuser

Superusers and table owners skip RLS. So every `transaction()` runs `SET LOCAL ROLE app_tenant` and `set_config('app.tenant_id', …, true)`. The `app_tenant` role (migration `0003_tenant_rls`) has no `BYPASSRLS`, so the policy always applies. Both settings are `LOCAL`: they end with the transaction, so a pooled connection never carries one shop into the next request. Without `app.tenant_id` the role sees no rows at all.

### Lint rule

ESLint blocks importing `DRIZZLE` from `…/database/database.module` or `…/database/database.tokens` in `src/modules/**`. Importing the `Database` type is fine. `src/modules/auth/**` and `src/modules/health/**` are exempt: login finds the user before the shop is known, and the health check pings the DB. Don't add more exemptions without a review.

### Review checklist for a new module

- [ ] Every business table uses `tenantColumns()` and `tenantIsolation()`.
- [ ] Every index starts with `tenant_id`; unique constraints include `tenant_id`.
- [ ] The migration has `ENABLE ROW LEVEL SECURITY` and the `tenant_isolation` policy.
- [ ] Services inject `TenantDatabase`, not `DRIZZLE`; queries use `scoped()` or its `where()` / `byId()`.
- [ ] No `tenant_id` in DTOs, params or query strings.
- [ ] Another shop's id returns `404` on read, update and delete.
- [ ] e2e isolation test with two seeded shops (read, update, delete across shops fail).
- [ ] Super-admin access goes through `withTenant()` only.
- [ ] Writes go through `scoped()` so they are audited; no `tx.delete(...)` on business tables (soft delete only).
- [ ] Restorable tables are registered in `RestorableRegistry`.

## Audit log and soft delete

- **Automatic:** `scoped(table).insert/update/softDelete/restore` write one `audit_logs` row each, in the same transaction as the change (if the log fails, the change is rolled back). The row has the shop, user, table name (`entity`), row id, `action` (`create`, `update`, `delete`, `restore`; `access` for super-admin `withTenant`), IP and user agent.
- **What is stored:** `create`/`restore` keep the new row in `after`; `delete` keeps the old row in `before`; `update` keeps only the changed fields, e.g. `before: { weight: 400 }`, `after: { weight: 420 }`. Keys that look like passwords, tokens, secrets, OTPs or hashes are stored as `[REDACTED]` (`src/database/audit/audit-diff.ts`).
- **Never hard-delete business data.** Use `softDelete`; reads skip deleted rows by default.
- **Restore (owner):** `POST /records/:entity/:id/restore`. A module makes its table restorable with `registry.register('traders', traders)` (inject `RestorableRegistry`, e.g. in `onModuleInit`).
- **Reading the log:**
  - `GET /audit-logs` (owner, own shop) with filters `userId`, `entity`, `entityId`, `action`, `from`, `to` (a date-only `to` includes that day), `page`, `limit` (max 100). It returns `{ data, meta }`, newest first.
  - Super-admin: `GET /admin/tenants/:tenantId/audit-logs`. That access is logged too.
- Sign-ins, sign-outs and failures are in `auth_logs` (see "Authentication"). Passwords, tokens and codes are never written to either log.
